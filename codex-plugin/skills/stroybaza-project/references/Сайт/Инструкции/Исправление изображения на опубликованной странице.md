# Исправление и замена изображения на опубликованной странице

Запрос «вот страница, здесь картинка плохо получилась; изучи, исправь и добавь вместо неё» означает полный цикл диагностики, подготовки и публикации замены выбранного изображения. Не ограничиваться советом или готовым файлом в чате, если пользователь поручил заменить на сайте и доступ есть.

Просто «посмотри/разбери» разрешает проверку, «подготовь исправление» — подготовку, а явное «замени/добавь вместо/исправь на сайте» — также необходимую загрузку и изменение. Обсуждение примеров команд или просьба доработать сам плагин не являются поручением менять эти страницы. Область действия — указанная страница, выбранная картинка и её связанные представления; не вся статья или сеть доменов.

## 1. Доступ участника — первый шаг

При поручении замены на сайте **сначала** проверить локально/через доступную интеграцию, есть ли у текущего участника сохранённый доступ именно к целевому домену. Сам плагин не содержит токенов автора, не передаёт их другим участникам и не создаёт API-доступ установкой.

Если доступа нет, **сразу задать вопрос**, до генерации и подготовки замены:

> Для замены изображения на `<домен>` нужен ваш API-токен доступа к этому сайту. Предоставьте токен или подключите готовый доступ.

Не откладывать запрос токена до момента, когда картинка уже создана. Для нового домена проверять доступ отдельно. Если этот участник уже подключил доступ к домену, повторно токен не спрашивать. Токен сохранять только доступным защищённым механизмом участника; не включать в инструкции плагина, Git, имена файлов, изображения, журналы и отчёты. Не выводить его при проверках. Если защищённого сохранения нет, честно обозначить доступный способ подключения и не обещать постоянную настройку.

Использовать имеющиеся инструменты сайта/подключённый API. Если в среде доступен навык `stroykerbox-access` или пользователь закрепил его в AGENTS.md, сначала прочитать его и взять домен/документацию/доступ по его правилам. Не рассчитывать на личный путь или хранилище автора на другом устройстве. В облачном чате нужен реально подключённый инструмент/доступ участника; наличие инструкции не означает наличие соединения.

Фактический запрос замены разрешает необходимые чтения, загрузку и точечную запись; повторное подтверждение тех же действий не нужно. До первого API-запроса сообщить пользователю **через API**, на каком домене и что будет прочитано/изменено. Затем проверить доступные поля и методы по актуальной документации/схеме этого домена. Не угадывать URL API, ID страницы, поле контента или формат загрузки. После этапа/ошибки сообщить результат и конкретное ограничение. При отказе авторизации или недостаточных правах сразу запросить актуальный доступ/нужные права, до генерации замены; не обходить отказ и не считать его исправленным.

## 2. Найти именно выбранное изображение

Открыть публичную страницу, её исходную картинку и при необходимости соседние кадры. Сопоставить описание, скриншот и видимый участок; определить роль (внутри статьи, превью, товар, тизер, акция или баннер), URL, размеры, место и связанные `srcset`/`picture`/ссылки увеличения. Применять правила именно этой роли: статья не превращает товар каталога в фотографию с логотипом. Не выбирать первое изображение автоматически. Если после просмотра цель всё ещё неоднозначна, уточнить только её.

Различать дефект исходника и отображения: форма/товар, цвет, плоская фактура, анатомия/руки, маркировка, неуместная сцена, кроп, масштаб, подпись/город, сжатие. Хорошую фотографию не перегенерировать из-за ошибки кадрирования или монтажа. Назвать обнаруженную проблему, разрешённую правку и сохраняемые свойства. Для практической статьи уместен профессиональный кадр со строителем/действием; исправление не обязано быть очередной раскладкой товаров, если проблема именно в выборе сюжета.

Прочитать текущие данные страницы через разрешённый API. Сохранить исходный файл и снимок соответствующего содержимого/ID/версии вне пакета плагина и Git, в рабочем месте задачи участника, для сравнения и возврата. Эти исходники/резервные копии не считать мусором уборки.

## 3. Исправить и принять изображение

Применить общий процесс точечной правки и профильные правила. Использовать лучший чистый мастер, если он есть; сохранить сюжет и фактуру при локальной коррекции. Для внутренних изображений обязательны полный X + СТРОЙБАЗА + город целевого домена. Для превью подпись не добавлять.

Если исходник уже содержит правильную подпись, сохранить её вне области редактирования и проверить после правки. Если используется чистый мастер или подпись испорчена/неверна — выполнить отдельный монтаж полного SVG. Не ставить второй знак поверх первого; при неправильном городе предпочитать чистый мастер. Проверить конечный WebP, размеры/вес, качество фотографии, подпись и город до публикации. Ошибку финального монтажа исправлять в слое, не новой генерацией фотографии.

## 4. Загрузить новый ресурс и заменить точечно

Загрузить **новый отдельный файл** штатным механизмом сайта/API. Не перезаписывать и не удалять старый файл: он может использоваться на других страницах и доменах. Возвращённый API адрес ресурса использовать для выбранного места страницы; в создаваемом/изменяемом HTML пути ресурсов должны быть от корня сайта. Подтвердить, что новый ресурс доступен и соответствует подготовленному файлу.

Непосредственно перед записью заново прочитать изменяемые данные. Если версия/хеш изменились, перенести свою точечную правку на актуальные данные, сохранив чужие изменения; не отправлять устаревший полный документ. Использовать условное обновление/ETag, если API его поддерживает. Если API требует полный объект, сформировать его из только что прочитанной версии и изменить исключительно нужное поле/фрагмент.

В выбранном месте обновить изображение и относящиеся к нему варианты/ссылки увеличения, сохранив смысловой alt, порядок, размеры/пропорции и остальную разметку. Не менять заголовок, текст, соседние фотографии, формы, стили, шаблоны и другие страницы. Если один URL встречается несколько раз, менять нужный экземпляр, не все совпадения строкой. Синхронизацию других доменов выполнять только по отдельному поручению, с их собственной подписью города.

Стили/скрипты в этой задаче по умолчанию не затрагивать. Если причиной оказался общий CSS/JS, не маскировать его перегенерацией фото; назвать причину и границы необходимого исправления. При отдельном поручении на CSS/JS работать с реально подключёнными файлами проекта по действующим инструкциям среды, а не с копией темы или произвольным inline-кодом.

## 5. Проверить опубликованный результат

Открыть публичную страницу после записи: правильное место, новый ресурс, качество/кроп, один полный логотип и нужный город, отсутствие изменений соседнего контента. Успешный ответ API сам по себе не доказывает замену; проверить фактический отображаемый файл и при необходимости его контрольную сумму/данные.

При ошибке вернуть только собственную замену из сохранённого снимка, если это не затирает появившиеся изменения других участников. Не откатывать страницу целиком вслепую. Если запись недоступна, сохранить подготовленный результат и назвать конкретную причину; не утверждать, что изображение заменено.

В конце сообщить ссылку страницы, какую картинку и дефект исправили, результат фактической проверки и оставшиеся ограничения. Логи инструментов не заменяют сообщение пользователю.

В обеих поставках есть `scripts/article-repair-plan.mjs`: формирует порядок и проверки области действия из уже определённого фактического поручения. По умолчанию публикационный сценарий без доступа возвращает `credentials-required` и ранний вопрос участнику. Начальное `canPublish: false` означает незавершённую подготовку: `reviewArticleRepairReadiness` разрешает переход к записи только после принятого конечного изображения, проверки доступа, загрузки отдельного ресурса и повторной сверки страницы. Это планировщик, а не CMS-клиент; действующие API/подключение и проверка публикации обязательны.
